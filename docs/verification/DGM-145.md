## 2026-10-30 Independent Same-Socket AC7 Closure

Result: **ACCEPTED for AC1–AC7**. This supplementary verdict closes only the
AC7 transport-coverage gap above; it does not change or erase any other
historical result or release gate.

### Independent real-HTTP rerun

I inspected and reran the retained
`app/test-results/DGM145-transportrepair/parent-same-socket-probe.mjs` using
Node **v26.12.1**. The first run's report was preserved before rerunning it.
Both runs passed the probe's assertions:

| Run | Arrange HTTP 200 | Following edit HTTP 408 | Socket reuse | Edit signal aborted |
|---|---:|---:|---|---|
| Parent run, preserved | 5,263.4216ms | 5,008.6899ms | Same socket; `request.reusedSocket === true` | Yes |
| Independent rerun | 5,276.2399ms | 5,010.7063ms | Same socket; `request.reusedSocket === true` | Yes |

The edit elapsed time is measured from the real HTTP request start through
response completion and is greater than 5,000ms, establishing the non-arrange
timeout on the reused connection. The test makes two sequential HTTP requests
through one `http.Agent` with `maxSockets: 1`, then asserts strict equality of
the socket objects and `request.reusedSocket === true`.

The probe starts `createMcpServer` on an ephemeral loopback port and sends
normal authenticated JSON-RPC `tools/call` requests through its HTTP handler.
The successful arrangement and the following edit's abort callback establish
that both requests passed authentication and RPC/tool schema validation and
reached the mutation callback. The callback is a controlled in-memory stub:
arrange resolves after 5,250ms; edit waits for its abort signal. No diagram or
persisted product data is changed. Source inspection confirms that auth and
validation precede `beginArrangement()`, which immediately precedes `mutate()`;
only arrange receives the 15,000ms request/socket window. The ordinary request
timer remains 5,000ms, and edit does not receive the arrangement extension.

### Client-side explanation and scope

The earlier apparent socket-reuse failure was caused by Node 26's default
client `agentKeepAliveTimeoutBuffer` of 1,000ms interacting with the server's
advertised 1,000ms keep-alive timeout: the client retired the free socket, so
the next request did not exercise the server's reused-socket cleanup path. The
probe sets **only the client-side** buffer to zero while retaining keep-alive
and one-socket limits. It does not modify server code, server timers, or
validation. This explains the earlier nonrepresentative connection; it is not
a server deadline relaxation. The previous different-socket and partial-body
observations remain preserved as historical evidence, not newly claimed fixes.

The probe's `finally` block destroys its client agent and awaits
`server.stop()`; the command exited successfully after cleanup. The original
parent report and independent run output are retained under the ignored
`app/test-results/DGM145-transportrepair/` directory. No production, test,
manual, or spec file was changed for this closure.
