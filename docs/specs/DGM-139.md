# DGM-139: Persistent Favorites Category

Date: 2026-10-28. Status: COMPLETE / INDEPENDENT SOURCE ACCEPTANCE PASS.
Authority: PO requested "for components, favorites must be a category and be
persisted."

## Context And Contract

Expose Favorites as a first-class category alongside existing component
categories, not a separate competing view/toggle or duplicated panel.
Reuse existing favorite/unfavorite interactions and stable catalog IDs.
Selecting Favorites filters to saved favorites and combines predictably with
component search. Show an honest empty state with how to add favorites.
Removing the last favorite while viewing the category leaves a usable empty
category, not a stale result or unexpected category switch.

Persist membership in application-profile preferences across library close/
reopen, page reload and desktop restart. Browser and desktop profiles retain
their own settings; no cross-device/shared-root synchronization is implied.
Favorites are not diagram data and must not enter document JSON, Undo history
or MCP diagram mutations. Preserve existing valid favorites/preferences rather
than replacing them when adding the category.

Reuse existing persistence where available; do not introduce a dependency,
database or migration unnecessarily. Validate stored shape and catalog IDs,
ignore unavailable IDs in results without deleting unrelated stored data.
Report storage read/write failures explicitly; never claim an unsaved toggle
was durably saved. Bound stored data and use safe fixed keys/typed data.

## Acceptance And Tests

- Given component categories, Favorites appears as a peer selectable category,
  reachable by mouse and keyboard in supported narrow/desktop/theme cells.
- Given favorite/unfavorite actions, membership/category results update and
  survive reload and an actual desktop profile restart.
- Given Favorites plus search, only matching favorites appear; empty results
  explain the state and remain actionable.
- Given malformed/unavailable storage, visible failure handling preserves
  unrelated preferences/document/history and does not fabricate persistence.
- Existing browsing/search/ranking/scroll/keyboard/add-component behavior and
  DGM-137's explicit-open/no-footer/no-pin contract remain intact.
- TDD, focused tests/typecheck/build and independent real browser/desktop
  persistence acceptance pass with retained first logs and owned profiles.
