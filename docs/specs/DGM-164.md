# DGM-164: Researched Azure architecture starter catalog

## Context and authorization

The PO requested a hierarchical catalog of architectures researched from
Microsoft Learn/Architecture Center, AWS, Google Cloud and relevant architecture
blogs, with an editable diagram, title and Markdown explanation for each.
The PO approved 24 **new** architectures, split 8 Microsoft-origin,
8 AWS-origin and 8 Google-origin; AWS/Google patterns become conceptual Azure
adaptations, not native other-cloud diagrams. Retain all 11 existing starters.
On 2026-11-06 the PO chose to replace the current Add Diagram picker with this
catalog rather than add a competing catalog page.

## Goal and scope

Make it practical to browse, understand and add an architecture to the current
workbook without losing existing work. Deliver the complete catalog and chooser
before consolidated validation. Do not interrupt implementation for
per-architecture test or documentation rounds.

## Interfaces and contracts

- Reuse the native editable Diagram model, current starter registry, scene/SVG
  preview and sanitized Markdown rendering. No new dependency or persisted
  schema is required.
- Preserve the 11 existing starter keys and their automation availability.
  Add stable keys for the 24 new entries through the existing template
  discovery/insertion paths; do not add a new public command or broaden
  workbook mutation permissions.
- Each new entry has an original title, workload category, source origin,
  Azure target, source URL(s), reviewed date, original Markdown explanation,
  mapping caveats and an editable native diagram. Provenance is visible in the
  catalog and accompanies the added diagram's Markdown.
- Original explanations cover purpose, components, numbered flows, appropriate
  use, limitations and source attribution. Adaptations are conceptual starting
  points, not deployed systems, certified vendor architectures or drop-in
  service equivalences.
- Use verified primary sources; relevant blogs are supplementary context, not
  authority to copy diagrams, prose or assets. Retain failed/inaccessible source
  results honestly. No remote scraping/runtime fetching is added to the app.
- Preserve pristine-startup initialization versus explicit append behavior,
  root promotion, page limit, unsaved-work guards, selection and Undo.

## UI direction

Extend the established application visual system; do not redesign the shell.
This is an Operate surface for architects choosing a useful starting point.

- Replace the thumbnail grid with a roomy two-pane catalog. A compact left
  navigator groups architectures by workload; expanding a category reveals its
  architecture titles. Blank remains available.
- The right pane owns the selected title, source-origin cue, large readable
  diagram preview and rendered Markdown explanation/source links. Selection
  previews only; an explicit Add Diagram action performs insertion.
- Keep category navigation and selection legible, with a clear current state.
  A simple search can filter title/category/origin without adding a separate
  browsing surface. A no-results state explains how to recover.
- Give the diagram most of the available right-pane width and a substantially
  larger viewport than the old grid thumbnails. Render only the selected
  diagram, not all 35 previews at once.
- Preserve explicit close/Escape, focus restoration, full keyboard access,
  sanitized links, light/dark themes and scroll reachability. Text-input arrow
  keys must edit text, not trigger dialog navigation.
- At narrow/short sizes, reflow navigation above the preview and retain a
  reachable Add/Close action. No horizontal page overflow or clipped content.
  Do not persist a new preference or modify user work just to browse.

## Acceptance cases

1. Given the completed registry, there are exactly 24 new entries with an
   8/8/8 origin split and the 11 existing keys still available. All keys,
   sources, category membership and diagram IDs are valid and unique.
2. Given any new entry, its native diagram parses and renders with valid
   endpoint/group references, Azure-targeted service labels, honest synthetic
   status, readable boundaries and short directional flow labels. Diagrams
   reflect distinct sourced patterns, not repeated stock topologies.
3. Given an AWS/Google-origin entry, its Markdown explicitly explains the Azure
   adaptation and material non-equivalences; no claim of automatic deployment
   or vendor approval appears. No copied source diagram/prose/assets are used.
4. Given the catalog, navigating categories and selecting a leaf changes the
   large preview, title and Markdown without changing the open workbook.
   Search and no-results recovery work if search is included.
5. Given an existing workbook, Add Diagram adds exactly one selected architecture
   page with title and Markdown, selects it, preserves previous pages and
   supports one-step Undo. Cancel/Escape add nothing. Blank and Add New Page
   retain their distinct existing workflows.
6. Given a pristine initial diagram, choosing a starter still initializes that
   page rather than creating an unwanted second page. Full-root Load/Save,
   maximum-page guards and existing template automation remain unchanged.
7. Given keyboard, light/dark, wide/narrow/short layouts, category selection,
   source links, close and insertion remain accessible and reachable. Focus
   stays in the dialog while open and returns to the opener when closed.
8. Given the completed implementation, consolidated relevant registry/parser,
   session/automation and chooser regressions plus TypeScript/Vite build pass.
   One independent bounded real-interaction/visual pass checks the completed
   catalog and representative architectures from all three origins. Repair
   confirmed defects with the same implementer and recheck affected behavior.

## Implementation and evidence plan

One researcher produces verified source/content inventory in ignored session
evidence. One implementer owns native entries, registry, chooser, tests and
repairs. The orchestrator owns this contract and consolidated closeout; one
independent verifier reports evidence without fixing production code.

Retain first failures and input provenance under
`app/test-results/architecture-catalog/`. Run tests/build/browser checks only
after the whole implementation is complete. Reuse unchanged DGM-163 acceptance.
Do not reload the user's running source/release windows or touch their drafts.
Consolidate manual/queue/decisions/verification documentation after acceptance.

## Out of scope and risks

No new dependency, security/network policy, persisted format, schema migration,
remote content importer, cloud deployment, native AWS/GCP variants, release
version bump, packaging/publication or user-profile changes. Source authorization
does not imply a new executable release.

Primary risks are inaccurate cross-cloud equivalence, stale sources, repetitive
content, unreadable graph layouts, unsafe Markdown links, keyboard traps and
loss of startup/append semantics. Review the sourced content, exercise actual
selection/insertion and render real diagrams rather than counting files alone.
