## Purpose And Boundary

This is a readiness contract for qualification of an explicitly approved,
current candidate. It completes the missing task paperwork; it does not qualify
a platform, adopt a support promise, build a desktop artifact, launch an app,
publish anything, obtain credentials or change source/configuration.

Historical Windows ARM64 package evidence is native only for its 2026-10-09
artifact. Historical Windows x64 runtime evidence was emulated on ARM64, not
native Intel/AMD. The macOS ARM64 workflow is a configured build path, not a
produced or launched Mac application. Neither historical evidence nor a green
source suite qualifies the current Sprint 4 candidate.

The default until every required cell has fresh evidence is: local source
candidate only, with no qualified platform or release/support claim. Missing
input blocks only its cell. It does not stop DGM-110/116 closure or local
documentation work. The orchestrator records blockers once and resumes other
ready work; it does not repeatedly seek the same decision.

## Future Execution Contract

Pseudocode for each authorized cell:

1. Verify the approved candidate hashes and target/device identity before launch.
2. Create an isolated, owned profile without touching existing user data.
3. Execute only the selected cell's frozen cases; retain command, output,
   screenshots/downloads and final exit result under `app/test-results/platform/`.
4. Exercise local persistence, lock/read-only behavior, JSON transfer, export,
   worker/layout, offline behavior and native input/output appropriate to the
   cell. Preserve original data and record failure/denial paths.
5. Independently verify the result, record PASS/FAIL/BLOCKED per cell, and keep
   platform-specific evidence separate. Route a confirmed product defect to its
   scoped owner; do not repair while verifying.
6. Continue independent cells. Mark the matrix aggregate `QUALIFIED` only after
   every PO-adopted required row passes; otherwise report its exact non-PASS
   cells without a support or release claim.

Existing commands are future evidence tools, not authorization to run them now:

```powershell
npm --prefix app run test:desktop
npm --prefix app run desktop:pack
npm --prefix app run desktop:pack:mac
npm --prefix app run desktop:verify
```

`test:desktop` checks shell/policy behavior only; it is not native runtime
qualification. Desktop packing, native launch, browser execution and manual
handoff require the per-cell authorization and inputs above.

| Case | Given / When / Then |

| AC113-4 native input/output | Given the selected desktop/browser target, when keyboard, IME, chooser/download/cancellation and export paths run, then target-appropriate evidence records actual result; adapter/session evidence alone is not a physical-dialog claim. |
| AC113-5 browser/manual boundaries | Given an adopted browser/manual row, when physical zoom, touch, Teams/Office or human scenarios are required, then real target evidence is captured or the row remains BLOCKED. |
| AC113-6 result aggregation | Given cells finish, when the matrix is summarized, then only adopted rows with independent PASS evidence are qualified; FAIL/BLOCKED rows and external prerequisites remain visible. |

## Ownership, Escalation And Definition Of Ready

The orchestrator maintains this contract and matrix. A release owner produces
only expressly authorized artifacts. A platform verifier executes/records cells
without source fixes. The confirmed defect owner uses ordinary TDD within a
separately frozen implementation scope, then returns the affected cell to the
verifier. Verifier-to-owner repair follows the roadmap's three-cycle limit;
manual/device blockers are external and do not consume repair cycles.

This task's documentation definition of done is met: it names evidence identity,
native separation, cell inputs, cases, ownership, output location and blocked
conditions without inventing a support matrix. Runtime qualification is ready to
dispatch only after the matching cell inputs and explicit bounded authorization
arrive. Packaging, signing/notarization, publication, CI, credentials, new
dependencies, data changes and support announcements remain out of scope.
