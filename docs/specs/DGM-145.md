# DGM-145: Align MCP Arrangement With The Native Layout Budget

Date: 2026-10-30. Status: SOURCE ACCEPTED / COMMIT AND TWO-TARGET REBUILD NEXT.

## Context And Authority

The PO explicitly approved "the arrange-only deadline change and rebuild both
packages". Only MCP `arrange_diagram` changes from a 4000ms broker budget to
15000ms, matching the existing native layout job limit. All output and other
mutation deadlines remain 4000ms. Both Windows 0.5.0 packages must be rebuilt
from newly committed source and independently qualified before publication.

DGM-144 Attempt9 recorded a genuine x64 4022.6ms broker expiry. Attempt12's
single instrumented retry completed in 2755.6ms, with 2437.0ms worker runtime;
the original variability remains unexplained. This is an explicit budget
contract decision, not a claim that the earlier cause was isolated or repaired.
The historical DGM-143 PNG timeout remains unresolved.

## Interfaces And Invariants

- Production broker dispatch, timer, `active` and `complete` use one correlated
  absolute deadline: 15000ms for validated `arrange_diagram`, 4000ms otherwise.
- Preserve existing explicit broker timeout overrides used by tests/callers.
  Do not add a user setting, environment variable or new dependency.
- Keep the renderer's native 15000ms job cap. Propagate the main-owned absolute
  deadline unchanged; do not extend or restart it after dispatch.
- Keep single-flight rejection, request IDs, disconnect/unload cancellation,
  expiry rejection, stale/ABA/state-generation guards and atomic history.
- No permissions, HTTP authentication, output shapes or output limits change.

Expected implementation surface is `app/electron/mcp-bridge.mjs` and directly
related deterministic broker tests. Inspect renderer deadline handling before
deciding whether it needs any change; do not modify it speculatively.

## Given / When / Then Acceptance

1. Given the default broker and a valid arrange request, when 4000ms passes
   but 15000ms has not, then the request remains active and a valid completion
   is accepted; the sent absolute deadline is exactly start plus 15000ms.
2. Given any other supported mutation or output request, when 4000ms expires,
   then it is cancelled/rejected at the unchanged boundary; no late result is
   accepted. Cover PNG snapshot and export explicitly.
3. Given arrangement at or beyond 15000ms, then expiry/cancellation occurs
   and `complete` cannot commit a late result. Cover the exact boundary.
4. Given disconnect, unload, explicit cancellation or stale generation during
   the longer arrangement window, then work is cancelled and no document or
   history mutation occurs; the next valid request can proceed.
5. Given an existing explicit broker timeout override, then its pre-change
   behavior remains intact, including arrangement. Invalid requests stay
   rejected before dispatch and overlapping requests stay rejected.
6. Given renderer/job handling, then its existing cancellation, worker cleanup,
   stale-operation and 15000ms native limit remain covered by unchanged tests.
   Never simulate a successful broker reply to bypass renderer acceptance.
